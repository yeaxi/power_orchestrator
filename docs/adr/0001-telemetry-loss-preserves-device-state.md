# Зберігати стан приладів за втрати телеметрії

Недоступність датчиків у встановленому Power Orchestrator спричиняє аварійний OFF, хоча вона сама не доводить втрату живлення; зафіксований інцидент мав близько 6.9 с недоступності. Користувач погодив зберігати стан приладів, блокувати нові команди, що потребують відсутніх даних, і лише повідомляти за Telemetry loss будь-якої тривалості. Після Telemetry recovery система автоматично очищає telemetry fault та відновлює моніторинг, без ручного clear_fault та без автоматичного ON через сам факт повернення даних.

## Consequences

- Відсутність даних сама не дає підстави для OFF навіть після тривалого таймауту; у цей час система не може гарантувати виявлення перевантаження. Це погоджений компроміс на користь збереження стану приладів і видимого повідомлення.
- Відновлення визначають чинні перевірки валідності та свіжості потрібних входів. Невідомі, несвіжі або суперечливі дані залишають керування blocked; пропуск даних не зараховується як тривалість підтвердженого перевантаження.
- Очищення охоплює telemetry fault latch, його активну причину в runtime і persisted state та активне повідомлення про цей fault. Історія інциденту зберігається; після перезапуску очищений telemetry fault не повертається зі сховища.
- Confirmed supply loss, підтверджене перевантаження, Quarantine, storage fault та невизначене виконання команди зберігають власні правила й gates. Повернення телеметрії очищає fault і блокування, спричинені Telemetry loss, та не змінює обраний режим.
- Це рішення змінює опис unavailable grid-safety у чинній проектній специфікації та telemetry all-stop/latch установленої версії 0.7.3. Реалізацію й специфікацію слід узгодити в окремому виправленні; runtime-поведінку цього рішення ще не перевірено.

Погоджені правила та межі перевірки: [тикет 02](../../.scratch/power-orchestrator-reliability/issues/02-telemetry-loss-policy.md), [докази triage](../../.scratch/power-orchestrator-reliability/spec.md).
